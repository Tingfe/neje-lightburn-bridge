# LightBurn 控制采集及批量查询稳定性修复

2026-10-12，本轮没有新增运动、出光、回零、设置写入或实际复位。新增的诊断入口只记录并拦截 `!`、`~`、`0x18`，其他数据仍受已有初始化白名单约束，不能与固定运动入口同时启用，不生成任何成功应答。

## 实测结论

- 真实 LightBurn 的停止按钮在本次 Idle/只读场景发送 `0x18`；两次捕获均在本机拦截，没有送入 NEJE。运行中停止的完整命令序列尚未确定。
- 空闲时、以及仅含 `$I` 的文件发送期间点击暂停，未捕获到 `!` 或 `~`。LightBurn 会把纯查询文件立即标为完成，控制器也保持 Idle；这一方法不能验证运动中的暂停/恢复。
- 串行查询修复后，同一份仅含 512 行 `$I` 的文件全部取得真实应答，另有 1 次初始化 `$I`。文件首条应答 20:26:15.563，末条 20:27:36.763，约 81.2 秒。此时间是大响应查询的实测，不是运动 GCode 吞吐基准。
- 成功会话共 709 个真实普通终端：513 次 `$I`、1 次 `$#`、5 次裸 `G0`、190 个空行。189 次公开 `?`，另有一次内部基线查询。45,305 接收字节全部核验，TCP 交付 45,215 字节，内部基线与公开 ACK 隔离，0 伪造 ACK、0 重放、0 重连拒绝。最大 GATT 写 73 字节。
- EOF 后无新业务写入，排队/在途普通行和状态查询均为 0；20:27:52 关闭读回 `way=0/app3`、w4480/r55386，设备错误计数 0；应用退出、TCP 服务关闭。

完整成功捕获与审计：`evidence/control-capture/lightburn-controls-03.jsonl`、`lightburn-controls-03-audit.json`。

## 本轮暴露并处理的问题

E48（20:17–20:18）：旧流水实现允许很多短 `$I` 共用输入字符额度。512 行查询文件开始发送后，接收序号从期望 4863 跳至 6263，出现 1400 字节缺口。主机停止发送并记录不确定写入，不重放。只能确认接收缺口，尚不能区分设备缓存、无线通知丢失或其他固件原因，不能宣称重传已经解决。

故障期间，接收任务发现流水已经锁定，而操作任务正在发送关闭通道命令；外层结束流程取消操作任务，打断了关闭读回，因此当时正确标记 `cleanup_unknown=true`。独立核查确认模型 55/app3，三次状态稳定、w2530/r10002，与本次尝试写入计数一致；路由已经是 0，没有再关闭，也没有发送 GRBL 文本。证据：`lightburn-idle-controls-01.jsonl`、`explicit-cleanup-01.jsonl`。不能把事后确认追认为原会话已完成清理审计。

E49（20:24）：修复后首次初始化仍返回真实 `error:3`，随后停止。旧会话尝试字节止于未完成的 `$`，与它同后续 `G0` 拼接导致系统命令错误相符；关闭通道并不保证 GRBL 半行被清除。没有伪造成功、复位或重发旧作业。真实错误及已送入的裸 `G0` 应答保留；修复后的关闭流程完成 `way=0/app3`，w2543/r10081。证据：`lightburn-controls-02.jsonl` 和错误截图。通用运动作业故障后的恢复仍需处理半行/未知执行状态，不能照搬这次只读初始化处理。

E50（20:25–20:27）：新会话初始化无错误，同文件 512 行查询全部通过，随后正常清理及完整捕获审计通过。失败记录均保留，没有覆盖为通过。

## 实现与验证

`tools/grbl_pipeline.py` 保留普通 GCode 的字符计数流水发送；`$` 系统查询新增前后屏障，必须等此前普通行排空，且查询真实终端到达后才发送下一普通行。大响应不会仅因查询本身只有几个输入字节就被批量积压。普通在途行另限 64，防止大量空行产生应答突发；实时状态查询仍可绕过普通窗口。

`tools/pipeline_tcp_bridge.py` 将会话关闭放在独立、有界、受保护的任务内，即使接收任务发现故障或 EOF 收尾取消操作，也会等待本次已开始的关闭完成；实际 BLE 断连仍如实标记清理未知，不自动重连或续跑。

继续借鉴已归档的 [GRBL 官方逐条应答脚本](https://github.com/gnea/grbl/blob/bfb67f0c7963fe3ce4aaf8a97f9009ea5a8db36e/doc/script/simple_stream.py)及字符计数脚本、cncjs 的普通发送窗口/实时命令分离。来源提交、散列、MIT 许可证见 `evidence/stream-transport/sources.json`。本轮查询屏障和清理竞争修复属于本项目实现，不宣称上游已经实现 NEJE 的接收缺口恢复。

138 项全套离线回归通过（24.446 秒），包括查询屏障、普通流水、状态绕行、空行数量限制，以及接收故障与慢清理竞争；随后新增的 2 项归属核验和 6 项捕获审计全部通过，含旧真实捕获回归、513 次真实信息查询、伪造 ACK 和虚假控制转发/成功标记反例。测试输出、当前源码快照及散列在证据目录中。

本轮推进了持续传输与清理可靠性，并取得真实停止请求字节证据。没有验证设备实际暂停、恢复或取消，也没有验证通用加工；[最终目标](usb-parity-goal.md)保持未完成。下一步应实现并离线验证作业控制状态机，再集中准备带暂停/恢复/停止的零功率运动对照，避免用更多纯查询实验替代作业控制验收。
