## 必须优先处理的发现

### F1 / P1：透明模式的 Stop/软复位在桥接内被拒绝

`tools/pipeline_tcp_bridge.py:155`在透明模式选择普通GrblPipeline；输入策略将0x18识别为cancel，接着在第125行调用pipeline.realtime。`tools/grbl_pipeline.py:66`仅支持?、!、~，因而抛出ValueError。受审模式的ControlledGrblPipeline有复位支持，但当前透明入口未使用它。

真实回环TCP + 原始NEJE分帧/计数层 + 假BLE设备的离线复现：客户端发送0x18后连接结束，错误为`Only explicit GRBL status/hold/resume bytes supported`，假设备收到复位次数为0。不是“设备收到停止但没响应”，而是根本未转发。现有策略测试只断言0x18被分类为cancel，没有接到真正的透明流水入口。

修复应包括实时停止的优先级、未发送队列废弃、复位后的应答代际/计数/状态与关闭，不宜只在允许字节集合里加0x18。原受审模式停止证据不能验收此透明路径。

### F2 / P1：GUI急停使用了Mac上不可用的Pi USB路径，并先宣称成功

`tools/neje_app.py:429`启动`emergency_stop.py --execute --log ...`，没有选择当前蓝牙链路或传入串口。`tools/emergency_stop.py:28`默认/dev/ttyACM0，且依赖serial；当前Mac桥接venv没有serial模块。第432行不等待子进程结果或真实状态便显示“已发送急停”。

无GUI窗口、无真实子进程的复现确认了上述argv和立即成功文案。工具本身可在Pi的USB上下文使用，但当前Mac蓝牙GUI按钮不能据此声称急停已发出。需要绑定当前所属连接，并区分请求、发送未知和设备已确认停止；失败时不得成功提示。

### F3 / P1：点动翻译改变GRBL语义并泄漏模态

`tools/passthrough_policy.py:39`至66把$J=固定改成`G91 G1 ...`，不保存或恢复G90/G91、G0/G1、F，不强制毫米或零功率。`G90 → $J=X1F100 → G1X10`被转成`G90 → G91 G1 X1 F100 → G1X10`，后一个X10就仍为相对移动。G20起始时“100mm”上限实际可能成为100英寸；M4/S100后翻译出的G1继承非零功率，不能视作规范点动。以上为源码及离线输出推导，未在设备上执行这些反例。

[GRBL官方点动规范](https://github.com/gnea/grbl/wiki/Grbl-v1.1-Jogging)说明：省略G90/G91时继承当前距离模式，且规范点动不修改解析器模态。因此G90状态下$J=Y-1本来就表示绝对Y=-1；已存“长距离运动”不能单独证明固件偏离标准。当前拒绝$J=G91...，反而拒绝规范的显式相对形式。实际零功率±1mm证据成立，但不能推出“USB意图完全一致”“不再可能跑飞”。

先查明真实USB/BLE对规范显式模态点动的行为，再决定兼容策略；如保留GCode适配，必须处理状态、单位、功率和取消语义，并增加对应实机对照。

### F4 / P1：端口检测会消耗桥接的一次性客户端

`tools/neje.py:112`和`tools/neje_app.py:77`用connect_ex检测端口。桥接在`pipeline_tcp_bridge.py:73`把任何第一个连接标记为used，再建立BLE/预检；检测连接不是被动检查。

离线实际回环复现：port_in_use返回True，同时仅检测就使桥接会话结束；随后真正客户端被拒绝。因此首次LightBurn连接前重复运行启动器，或某些GUI端口检测路径，可能令“已在运行”的服务立即退出。应使用不创建业务连接的拥有者/监听状态检查或单独健康接口。复现只用了随机本机端口，没有访问真实4002。

### F5 / P1：所谓独立透明审计不足以支撑其结论

`tools/check_transparent_capture.py:73`只检查交付字节是否包含在原始staged数据中；第78行只核对每行after=before+长度，没有跨事件连续性或原始通知/CRC/真实设备快照对应证明。它还复用运行中的PassthroughPolicy计算期望转换。

对真实D级捕获创建单独篡改副本：删除所有pipeline_tcp_delivered事件，审计仍passed=true且bytes_delivered=0；把每个写计数before/after均加100，使其与实际帧及确认计数不一致，也仍通过。原始捕获未被修改。空交付不能证明无伪造或完整回传，单行长度正确不能证明计数连续；输出passed还可能伴随clean_shutdown=false。

需复用或等价实现现有严格原始帧审计，核对notify→frame→CRC→收发计数→confirmed数据→公开交付/明确废弃→终端应答所有权及完整清理。已执行更严格的独立复审：既有透明D级和最新实际初始化两份原始捕获均通过，说明该发现是审计覆盖不足，不是指控这些捕获造假。

### F6 / P1：GUI不以审计/清理结果决定故障后能否重启

`tools/neje_app.py:177`至191在子进程退出后读取审计结果，但不检查fail/pending/cleanup_unknown便安排下一次_spawn。离线复现中审计fail后仍安排并生成下一次桥接。新进程不会自动使远端所属路由、半行、位置和任务状态可信。底层可能拒绝仍活跃路由，这不等于监督器建立了正确恢复门槛。

仅在明确正常结束且所需状态可核验时自动准备新连接；其余应保留失败并进入显式恢复。不会重放GCode的事实，不等于不会自动重新连接未知设备。

### F7 / P2：自动LightBurn配置端口写入位置与当前实际模式不一致

`tools/device_setup.py:143`向设备顶层写NetworkPort，当前LightBurn2.0.05经实际UI持久化的是Settings.NetworkPort。模板若已有Settings.NetworkPort=23，纯离线build_device会保留23同时另写顶层4002。应采用实际持久化结构，并通过新建/重开UI验证；当前只证实字段冲突，没有把上一轮默认23的原因追认为此生成器。现有手动修正后的设备Settings.NetworkPort=4002仍正确。

### F8 / P2：本机打包产物落后于当前源码

本轮仅以--help和--dry-run运行dist/neje：沙箱先被macOS信号量限制阻止，宿主离线两项均退出0，没有连接设备。打包CLI的帮助仅含--test/--dry-run/--check，当前tools/neje.py还有--valid-for；.app仍是Terminal启动壳。可确认产物可启动且与源码接口不一致，不能将本轮源码397项结果套用到未重建的二进制，也没有验证Tk GUI成品。应按当前版本重建并另行验收。

## “100%”的证据问题

- `multi-hour-result.json`明确是Pi USB有线运行2小时13分25秒，不是BLE，更不是当前透明/GUI通路的数小时证明。
- `stop-latency.json`来自USB软件时间戳和复位后的控制器位置；263ms是报警到达延迟，202ms采样周期及复位后坐标不可信，不能推出独立实测“<20ms停止、≤0.02mm”。未否定此前现场确实停住。
- 加工源指令/状态一致不代表成品深浅已经等效；USB痕迹偏淡未在一致对焦/材料条件下排除，也没有定量尺寸数据。已完成基本加工对照，不应称完整所有效果。
- README把“断链/程序退出不会停止已缓冲作业”扩大为“所有软件停止都不能停”不成立：旧受审链路有真实0x18停止记录及现场确认，当前透明链路又确实存在未转发Stop的缺陷，应区分这些情形。
- README推荐任意设计直接Start，daily-use-guide却仍要求导出、摘要和受审profile；transparent-bridge-plan仍标“未实施”，而源码和真实证据已实施；不同路径需要各自明确范围。
