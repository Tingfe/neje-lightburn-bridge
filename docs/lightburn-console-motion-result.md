# 真实 LightBurn 控制台受控运动：分会话完成（2026-10-12）

在用户重新确认现场条件并授权新增一次 1 mm 往返后，实际 LightBurn Pro 2.0.05 经本地 TCP 与 Mac CoreBluetooth 原生 BLE 发送运动；没有树莓派中转，没有点击开始加工。

## 首次前进与停止

18:41:48，LightBurn 控制台发送唯一 `G53 G1 X1.000 F60.000`。原始 BLE 收到两份连续数据：r=23459 的 `ok\n`，r=23462 的 `[MSG: Laser temperature:27.1C]\n`（31 字节）。设备计数 w/r=505/23493，错误0。

旧 InitSession 终结行后调用 exchange 清空帧队列，丢弃已收到的温度通知，导致本地 r 比设备少31。桥接按规则停止，没有交付成功、没有自动返程、没有重发。清理 way=0/app3。USB 只读复查两次 Idle、MPos=1/400/0/0、FS=0/0，模态 G1/G21/G90/G94/M5/S0/F60。

这是主机实现缺陷，不能归因于设备丢包；全部原始帧足以解释计数差。

## 修复与明确授权返程

用户再次现场确认，仅授权剩余 LightBurn 返程。修复 InitSession 的计数核验流程：不清空终结行后帧，逐帧累计真实数据再核验设备计数；保留温度通知交付，额外终结行/报警仍停止。未关闭计数检查，未伪造 ok，也未重放原前进。

18:43:36–38，新单连接桥接直接从返程授权阶段开始。LightBurn 控制台仅发 `G53 G1 X0.000 F60.000`。每步重新查询设置、偏移、模态、状态后才发送。此次仍收到分开的真实 ok 和温度通知，修复后核验成功，内部轮询至 Idle/MPos=0/400/0/0 后交付真实响应。控制台截图显示该返程行、ok、温度通知以及后续 X=0 状态。再从控制台发送裸 G0，收到真实 ok，退出 LightBurn，EOF 正常关闭读回 way=0/app3。

**应用入口的前进和返程实际发送及控制器终点得到验证；一次连续、无异常的完整 LightBurn 往返尚未验证。** 不把两次会话拼成一次无异常测试，不扩展为作业流或加工验收。最终只读状态与模态见 `final-controller-readonly.jsonl`，F60 保留，其他轴不变，M5/S0。
