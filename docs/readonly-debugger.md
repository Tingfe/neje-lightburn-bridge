# USB/BLE 只读调试工具

`tools/readonly_debugger.py` 提供统一的交互式命令行入口，复用已验证的 NEJE `ReliableSession`、固定 GRBL 查询编码和开源 Bleak/pySerial。终端显示状态、真实响应和 BLE 计数；完整原始数据、故障及恢复过程另存 JSONL。没有网络监听，也没有任意 G-code 输入框。

## 在树莓派上使用

本轮临时文件位于 `/tmp/neje-p0-20261012/`。依赖安装在该目录的 venv，系统 Python 和服务配置未更改。临时目录重启后可能消失，项目文件夹中的源码和证据是持久副本。

在已经确认激光模组供电物理隔离的实验环境执行，日志文件必须尚不存在：

```sh
cd /tmp/neje-p0-20261012
./venv/bin/python readonly_debugger.py --execute --laser-power-isolated \
  --ble-device 88:7D:F9:55:7B:0F --log ./my-session-01.jsonl
```

不带 `--execute` 只打印离线计划，不扫描、不打开串口。

| 命令 | 行为 |
| --- | --- |
| `connect usb` | 打开 NEJE 稳定 by-id 串口，115200，DTR/RTS 预置 false；先被动接收 2 秒 |
| `connect ble` | 扫描指定设备，核对型号 55/app=3/way=0，再临时启用可靠通道 |
| `build` | 仅发送 `$I\n`，显示核验后的版本响应 |
| `status` | 仅发送 `?`，显示核验后的状态响应 |
| `state` | 不访问设备；显示连接状态、最后核验结果、BLE 拥有通道的计数、历史中断查询标记 |
| `disconnect` | 正常关闭当前后端；BLE 读回 way=0/app=3 后断开 |
| `recover` | 仅故障状态可用；显式检查并清理本进程拥有的通道，回到 disconnected；不重发查询、不自动开始新会话 |
| `quit` | 退出并尝试清理；若仍处于 fault，退出码 2，不能据此认为设备通道已关闭 |

正常 USB/BLE 对照：

```text
connect usb
build
status
disconnect
connect ble
build
status
disconnect
quit
```

故障后先执行 `state`，再执行 `recover`。恢复完成后必须另行输入 `connect ble` 或 `connect usb` 才会开始新会话。`recover` 不等于知道上一条查询是否执行；历史“执行结果未确认”标记会保留，最后核验结果带有后端、目标和时间，不把旧结果冒充当前状态。

`--commands 'connect usb;build;status;disconnect;quit'` 可用于可重复的固定步骤测试，首次错误即停止；任意 GRBL 文本、G0、$#、复位等输入均不在命令集合。`--verbose` 可在终端打印全部 JSON 事件；默认只显示摘要。

## 恢复边界

BLE 通道归属仅保存在**当前进程**中，包括启用前基线、最后核验计数、至多一条在途查询。恢复会核对同一地址、型号、应用及计数范围，连续三次读回状态一致后才允许关闭 way=2；计数越界、非 0/2 通道、设备错误、应用变化都停止恢复。关闭后再次检查 way=0、app=3、计数不变。USB 恢复只确认主机串口关闭，不声称物理执行状态已知。

需要独占实验设备；计数只能检测部分干扰，不能证明没有其他软件碰巧发送了相同长度的命令。不要同时运行 LightBurn、旧桥接或厂家客户端。**进程崩溃/重启后不自动导入旧通道归属，不自动接管 way=2**；需使用既有独立检查流程和原始日志确认后处理。当前还没有跨进程恢复功能。

BLE 连接阶段一旦收到本客户端断开回调，就取消连接任务，防止 Bleak/BlueZ 内部继续连接后启用通道；旧客户端的延迟回调不会使新客户端进入故障。已建立连接后没有自动重连或自动重发。USB 控制线未做物理测量，预置 DTR/RTS 不等于证明驱动没有瞬时变化。

## 本轮验证与证据

见 `evidence/readonly-debugger/`：双后端原始记录、真实在途断链恢复记录、单元/回归输出、安装记录、最终环境及源码哈希快照。第一次双后端实测暴露连接阶段回调问题，保留为 `pi-dual-01.jsonl`；修复后的成功对照另存，不能把失败记录计作成功。

- `pi-dual-02.jsonl`、`pi-dual-03.jsonl`：两次成功的 USB $I/? → 断开 → BLE $I/?；最后读回 way=0/app=3。第三轮 BLE 状态包含 WCO，响应为 90 字节，计数按真实长度核验，不固定假设所有状态响应均为 62 字节。
- `pi-dual-03-console.txt`：默认摘要界面的真实终端输出。
- `pi-recovery-01.jsonl`：第二条 $I 在途断链，设备 289/16365→292/16427；仅第一条 $I 交付为 result。四个入口被 fault 拦住，recover 关闭读回 0/app3，再独立 connect/status 成功，最终计数 293/16489。
- `capture-audit.json`：三个成功捕获的发送白名单、版本/状态结果与已核验数据逐字匹配、恢复不重发及最终状态审计通过。
- `tests.txt`：39 项测试通过（原有 26 项及新增 13 项），覆盖计数回绕、越界拒绝、恢复状态、旧回调、连接阶段断开、部分 USB 写入与响应边界。
- 最终环境无测试 4002 监听，串口 fuser 无可见占用、蓝牙停止扫描；实际断开以日志 is_connected=false 为依据。最终 bluetoothctl 查询显示设备对象不可用，不能将这一输出单独当作断开证明。用户 SSH 主连接保留，没有常驻服务。

源码快照对应交付版本；初次失败、第二轮对照和恢复实验按开发过程保留，后续还加入了旧客户端回调保护及终端摘要显示，相关变化有测试覆盖。

这是开发阶段只读命令行工具，LightBurn 初始化错误仍存在；不提供加工、重传、跨进程恢复、无线衰落或设备断电后的自动恢复保证。
