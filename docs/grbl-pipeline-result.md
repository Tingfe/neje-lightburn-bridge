# GRBL 流水传输核心与真实 USB / BLE 只读对照

2026-10-12。目标仍是实际LightBurn经Mac原生BLE达到USB操作效果。本轮把“逐条等待一个ok”的固定小作业实验推进到有界流水传输核心，且用真实设备完成批量只读对照；没有新增运动、出光、暂停/恢复或实际加工。

## 实现

新增`tools/grbl_pipeline.py`，接收调用方已审查的完整命令行，提供有界发送队列、按真实终端应答释放的字符窗口、GATT载荷分块和独立实时字节队列。普通行可在前一行尚未收到ok时继续发送，并保留原始空白、注释及CRLF；整行接收额度在第一段发送前保守预留，跨BLE帧的半行保持顺序。

每帧载荷由实际特征上限减9字节可靠帧开销得出，再限制于NEJE编码器的256字节上限；不能把一个完整NEJE帧盲目拆成多个GATT写入。发送前预留字节，失败或取消后锁定停止，没有重发/重连/续跑。NEJE计数证明的是可靠字节传输，GRBL ok证明的是命令接收/处理，二者不是机械完成证明。

普通终端应答按FIFO对应完整已尝试发送的行；MSG、参数和状态数据不释放普通命令额度。`?\n`是实时`?`加一个独立普通空行，空行实际ok单独对应，不能丢掉这个ACK关系。状态/hold/resume可以绕过满普通窗口或半行，但hold/resume目前仅离线模拟，没有新的现场授权或实机试验。软复位字节不支持。

RX预算必须由调用方在已验证Idle/FS0后明确传入；本次实际初始Bf报告1500，借鉴cncjs留8字节余量，预算1492。运行中Bf是瞬时剩余空间，不应当作总容量反复重设。LightBurn仍有自己的发送窗口，该核心不替LightBurn生成应答。TCP背压、权限策略、查询超时、前后机械状态核验和EOF/清理由桥接调用方负责；核心没有设备发现或实机CLI，不是已交付的通用加工桥接。

## 开源依据

沿用已固定提交的gnea/grbl官方`doc/script/stream.py`：普通行长度记账、终端应答释放FIFO额度、异步输出不计ACK；借鉴cncjs `GrblController.js`的字符计数发送器和仅空闲时依据Bf调整容量的约束。没有照搬默认128/120字节到NEJE，也没有复制旧Python2脚本或cncjs完整控制器。原始来源、commit和散列在`evidence/stream-transport/sources.json`，cncjs MIT许可证同目录已归档。

## E42/E43 真实只读对照

`check_pipeline_host.py`及`check_pipeline_usb_host.py`默认离线，执行仅允许固定一个基线`?`、同一48字节批次中的16条`$I\n`、一个结束`?`。BLE发送前额外守卫、USB固定字节守卫均不允许其他业务写入；没有TCP公开端口。

| 项目 | E42 Mac原生BLE（19:34） | E43 Pi USB（19:35） |
|---|---|---|
| 固定业务写入 | ?、48字节批次、? | 完全相同 |
| 命令响应 | 16份真实VER/OPT/ok | 与BLE逐字节相同 |
| 总响应 | 1131字节全部CRC/序号/计数核验 | 1116字节与实际串口读取一致 |
| 初始状态 | Idle/X0/Y400/FS0，Bf100,1500 | 相同基础状态 |
| 中途状态 | Bf100,1500 | Bf100,1458，查询打断批次时仍有42字节待处理 |
| 清理 | way0/app3、w1414/r46809，设备错误0 | 串口关闭 |

BLE实际一个可靠写入载荷48字节，完整GATT帧57字节；实时查询在第一份批次终端应答被记录前已发送，证明这次不是逐条等待16次ok。27完整帧与原始通知重组一致，11字节系统通知尾部未完成且没有用于判定查询/清理。两条状态整行不逐字节相同：Ov字段和Bf瞬时值有差异，审计没有抹平这些差异。

`tools/check_pipeline_capture.py`独立审计原始通知/串口字节、固定发送序列、FIFO终端映射、真实16份应答一致及清理。证据在`evidence/grbl-pipeline/`，可离线复现：

```sh
/Users/tyongs/neje-ble312/bin/python tools/check_pipeline_capture.py
```
